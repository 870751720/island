# 自有服务器联机信令

## 背景

游戏使用 WebRTC 房主权威联机。房间发现和连接信息交换可部署到已有服务器，与云存档分开维护，减少对公共信令节点的依赖。

## 需求描述

在与 `server/` 同级的 `signaling/` 提供独立信令服务，默认使用已有服务器的 HTTPS 入口。服务只帮助玩家找到彼此并交换握手信息，持续游戏数据通过玩家直连。

## 设计方案

- 使用独立 Mosquitto 容器复用客户端现有 MQTT 协议；自有入口为 `wss://43.110.116.98/signaling`，免费保底为 `wss://broker.emqx.io:8084/mqtt`，服务器站点、Pages、H5 使用相同的优先顺序。客人首次连接、订阅失败或超时，以及未找到房间时，清理当前尝试并转到备用节点；两个节点都失败才报错。
- 房主先在自有节点完成连接与订阅，自有节点失败后才等待备用节点开房。自有节点正常时，备用监听在后台建立，不延迟开房；后台失败每 5 秒重试，退出后立即停止。两个节点登记相同房间码，解决只有一方无法访问自有节点时的发现问题。客人只在一个节点查找和握手，查房期间每秒重发 join，兼容后台监听稍晚完成。
- 房主以“节点索引 + peer ID”区分握手路由，ready、offer 与 ICE 沿客人进入的节点回复；客人每次节点尝试使用独立 peer ID，迟到消息不污染新尝试。收到 ready 后固定当前节点，不在 WebRTC 握手阶段迁移；重试仍由原有退出/重新加入流程负责。
- 使用六位直连房间码及 `island-game/v1/<code>/up`、`island-game/v1/<code>/down/<peer>`。房主接收 join 后返回 ready 并发送 offer，客人返回 answer，两端交换 ICE。
- Nginx 处理 TLS 与 WebSocket Upgrade，容器私网转发至 9001。30 秒 MQTT 保活配合 75 秒代理超时，房主持续在线接待新加入及重连；不转发持续游戏状态。
- 不引入 TURN，不改变 STUN。自有信令不能保证所有 NAT/运营商网络可直连，握手仍独立限时 30 秒；失败继续反馈给用户。
- 房主继续通过 `Actions.ts` 权威结算；客人动作上行、快照回流及事件补播全部沿用 WebRTC 双通道，不新增同步字段、存档字段、图鉴条目或版本号。
- 不持久化房间和握手数据，禁用 retained 消息。ACL 只开放两个游戏主题形状，但匿名客户端仍能访问匹配的主题，不宣称提供房间级鉴权。单消息体 32 KiB、包长 64 KiB、连接上限和容器资源限制控制资源占用。
- 信令中断不主动关闭已建立的游戏数据通道；房主在同一节点自动重连。自有服务重启期间新客人可转到备用节点；两个节点均不可用时无法新建连接，已建立的 WebRTC 连接按原心跳规则判断存活。
- 发布包包含 `signaling/`。Compose 先等待信令健康，再启动代理；部署验收额外通过公网 WSS 检查 MQTT CONNECT/CONNACK，失败沿用回滚流程。

## 验证与上线

`node scripts/test-multiplayer-connection.mts` 验证自有优先、双方或仅一方无法访问自有节点、连接/订阅超时、备用监听延迟、双向握手路由、迟到消息隔离、取消与资源回收。公共节点只作尽力保底，不保证其可用性或网络穿透成功。类型检查与 H5 构建后生成固定本地验证入口。实际服务启动和 WSS 验收需要服务器环境；仅构建前端不代表后端已上线。

首次联调可按部署文档的后端联调流程仅启用信令和代理路由，保留线上前端，随后由用户用新版本进行双机建房、加入、重连验证。用户明确确认后才执行正式站点检查和 `npm run deploy`。混用旧客户端时，能否查到房间取决于双方共同可达的节点，建议双方均更新。

公共备用使用 [EMQX 官方免费公共服务](https://www.emqx.com/zh/mqtt/public-mqtt5-broker)的 WSS 8084 入口；可用 `node scripts/test-signaling-service.mts wss://broker.emqx.io:8084/mqtt` 检查实际 TLS、MQTT 和双端查房信令收发。
