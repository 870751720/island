# Game 模块渐进拆分

## 背景

`src/game/Game.ts` 同时承担游戏装配、玩法入口、联机协调和表现层调度。持续在单一文件内扩展会提高修改冲突与回归风险，因此采用保持公开接口稳定的渐进拆分方式。

## 需求描述

- 不改变玩法、触屏交互、存档格式或联机协议。
- 每次只迁出职责边界清晰、可独立类型检查的模块。
- `Game` 继续作为 UI 和联机层使用的门面，避免调用方随内部拆分反复变化。
- 每一步均可独立提交和回退，全部完成后再部署。

## 设计方案

当前边界如下：

- `GameConfig.ts`：游戏级时间、距离和表现参数。
- `GameTypes.ts`：构造选项及游戏编排层内部共享类型。
- `presentation/PickupPresentation.ts`：拾取来源缓存、道具飞行动效、同帧提示合并与屏幕投影。
- `systems/ToolCycle.ts`：工具循环候选和可放置物品排序策略。
- `Game.ts`：保留生命周期装配、公开门面、房主权威结算与跨系统流程编排。

联机行为保持原有方向：客人动作继续上行至房主权威结算；拾取事件仍由房主广播，客人只补播其他玩家表现；本地玩家的拾取表现继续由 HUD 差额触发。拆出的模块不引入新的持久化字段或网络消息。

后续拆分优先选择 HUD 快照构建、存档装配和设施交互门面。涉及多个系统的权威事务继续留在 `Game`，直到已有显式上下文对象可以承载依赖，避免用大而宽泛的依赖接口机械搬运代码。

## 迭代记录

- 第一阶段：迁出配置与共享类型、拾取表现协调、工具循环策略；保持 `Game` 的公开 API、存档版本和网络协议不变。
